Bloque 0 · El gancho

El almacén que aceptó basura

La clase pasada montamos la base de datos de Rappi y guardamos 500 predicciones. Quedó hermosa: persistente, consultable, auditable. Ahora la empresa automatiza el pipeline para que corra solo, cada madrugada a las 3am, y meta los datos nuevos a esa base.

Una noche cualquiera, el proveedor de la API cambia el formato sin avisar: los precios empiezan a llegar como texto. El pipeline corre, no da ningún error, y guarda los datos en nuestra base.

?
El pipeline guardó los datos corruptos y no dio ningún error. ¿Cuál es el problema real aquí?

El problema no es solo que los datos estén malos. El problema es que nadie se enteró. El pipeline corrió "exitosamente" guardando basura. La base de la Clase 2 ahora tiene datos falsos adentro, y se ve igual de sana que siempre. El verdadero peligro de los datos malos no es que existan: es que pasan desapercibidos.

🔗 Conexión con la Clase 2
¿Recuerdas el auditoria.py con que le preguntábamos cosas a la base? Imagina correrlo hoy sobre datos corruptos: daría respuestas con total seguridad… y todas estarían mal. La auditoría no sabe distinguir un dato bueno de uno malo. Ese es el hueco que la Clase 2 dejó abierto y que hoy cerramos.
?
¿En qué momento nos daríamos cuenta del problema, si nadie está vigilando?

Tarde. Probablemente cuando el equipo de negocio ya tomó una decisión con esos datos y los resultados no cuadraron. Para cuando alguien investiga "por qué los números estaban raros", la plata ya se gastó. Necesitamos enterarnos a las 3am, no tres semanas después.

Bloque 1 · Teoría desde cero

¿Qué es calidad de datos?

Antes de definir nada, veamos el daño en vivo y con números. Esto es lo que pasa si guardamos el feed corrupto y le preguntamos algo de negocio.

El promedio mentiroso

$36.715
Promedio REALsobre los 200 pedidos sanos
$37.049
Lo que responde la basecon los datos corruptos adentro
La base promedió solo 160 de 200 pedidos — ignoró el 20% de los datos en silencio, y respondió como si tuviera todo.

El problema no es el tamaño del error (hoy se parecen por casualidad). Es que el promedio se calculó ignorando silenciosamente 40 pedidos que llegaron como texto. Un número que se ve bien y está mal es más peligroso que un error que se ve.

📦 Definición técnica
Calidad de datos es el grado en que los datos cumplen las condiciones necesarias para usarse con confianza. Se mide en varias dimensiones: que estén completos, en el tipo correcto, dentro de rangos válidos, y con la estructura esperada.
🌍 En la vida real
Es el control de calidad en una fábrica de empanadas. No revisas una empanada al inicio del día. Pones un inspector en la banda que revisa cada una que pasa, y suena una alarma si sale una mala. Hoy construimos ese inspector, pero para los datos.
?
En la Clase 1 limpiamos los datos a mano y quedaron perfectos. ¿Por qué no basta con eso?

Porque la limpieza de la Clase 1 arregló los datos de ese día. Pero el pipeline recibe datos nuevos cada madrugada, de un proveedor que puede cambiar el formato cuando quiera. La calidad no es una tarea que se hace una vez, sino una vigilancia que corre cada vez que llegan datos nuevos.

Las 4 dimensiones que vigilamos hoy

1
esquema
¿Tiene la estructura esperada?

Las columnas correctas, con los nombres correctos.

2
tipo
¿Los tipos son correctos?

El precio es número, no texto.

3
completitud
¿Está completo?

No faltan calificaciones.

4
rango
¿Los valores tienen sentido?

Una calificación está entre 1 y 5, no es 8.

Bloque 2 · Preparar el escenario

El feed sano y el corrupto

Para aprender a detectar problemas, necesitamos datos con problemas. Creamos dos archivos: el feed sano (como debería llegar) y el corrupto (la madrugada del desastre). Así probamos que el inspector aprueba el bueno y rechaza el malo.

🔗 Conexión con la Clase 2
Allá usamos random.seed(42) para que todos generáramos las mismas 500 predicciones. Hoy usamos la misma idea de reproducibilidad para que todos tengamos el mismo feed corrupto, con los mismos errores en las mismas filas.

Qué hace este bloque

Crea 200 pedidos sanos y los guarda en feed_sano.csv. Luego hace una copia y la ensucia a propósito, y la guarda como feed_corrupto.csv.

rappi_calidad/generar_datos.py
import pandas as pd
import numpy as np

np.random.seed(42)

N = 200
categorias = ["Pasta", "Pizza", "Sushi", "Burgers", "Postres", "Bebidas", "Ensaladas"]
ciudades = ["Bogotá", "Medellín", "Cali", "Barranquilla"]

df = pd.DataFrame({
    "pedido_id": [f"PED{1000+i}" for i in range(N)],
    "restaurante_id": np.random.randint(1, 51, size=N),
    "categoria": np.random.choice(categorias, size=N),
    "ciudad": np.random.choice(ciudades, size=N),
    "precio": np.round(np.random.uniform(8000, 65000, size=N), 0),
    "calificacion": np.round(np.random.uniform(3.0, 5.0, size=N), 1),
})
df.to_csv("feed_sano.csv", index=False)

dfc = df.copy()
dfc["precio"] = dfc["precio"].astype(object)
idx_texto = dfc.sample(40, random_state=1).index
dfc.loc[idx_texto, "precio"] = dfc.loc[idx_texto, "precio"].apply(
    lambda x: f"${int(x):,}".replace(",", "."))
idx_nulos = dfc.sample(15, random_state=2).index
dfc.loc[idx_nulos, "calificacion"] = np.nan
idx_rango = dfc.sample(8, random_state=3).index
dfc.loc[idx_rango, "calificacion"] = np.round(np.random.uniform(6, 10, size=8), 1)
dfc = dfc.rename(columns={"ciudad": "city"})
dfc.to_csv("feed_corrupto.csv", index=False)

print("Feeds generados: feed_sano.csv y feed_corrupto.csv")

Bloque 3 · Primera guarda

Que el pipeline no muera en silencio

Hoy, si la API no responde o el archivo no existe, el pipeline revienta y se detiene en seco. En un proceso automático de las 3am, ese error lo ve… nadie.

📦 Definición técnica
Una excepción es un evento que interrumpe el flujo del programa cuando algo sale mal. El bloque try / except permite intentar una operación riesgosa y reaccionar si falla, en lugar de que el programa entero se caiga.
🌍 En la vida real
Es el cinturón de seguridad. No evita el choque, pero controla lo que pasa cuando ocurre. try = manejas normal; except = qué haces si chocas.
🔗 Conexión con la Clase 2
¿Recuerdas el peligro del commit olvidado, ese error silencioso que dejaba la base vacía sin avisar? Hoy enfrentamos la misma familia de problemas: fallas que no gritan. La diferencia es que hoy aprendemos a hacerlas gritar a propósito.

Bloque 4 · Validación

Detectar que el formato cambió

El daño más peligroso es silencioso: el archivo se lee bien y los datos están corruptos. Necesitamos revisar el contenido activamente antes de confiar en él. A eso le llamamos validar la integridad.

📦 Definición técnica
Validar la integridad es comprobar que los datos cumplen reglas antes de usarlos. El esquema es la forma esperada (qué columnas, de qué tipo); validar el esquema es confirmar que esa forma no cambió.
🌍 En la vida real
Es el control de migración en el aeropuerto. El oficial revisa que estén todos los campos y que tengan sentido antes de dejarte entrar — no cuando ya estás causando líos adentro. Validamos en la puerta, no después.
🔗 Conexión con la Clase 2
Allá, al definir la tabla, le pusimos tipos a cada columna (Float, String). Esa rigidez daba integridad: la base rechazaría texto en una columna numérica. Hoy llevamos esa idea un paso antes: lo detectamos nosotros mismos, con mensajes de negocio, antes de intentar guardar.

Qué hace este bloque

Define qué columnas esperamos y una función que acumula en una lista todos los problemas que encuentre.

clase3.ipynb · celda nueva
ESQUEMA_ESPERADO = {"pedido_id", "restaurante_id", "categoria",
                    "ciudad", "precio", "calificacion"}

def validar_feed(df):
    errores = []

    if set(df.columns) != ESQUEMA_ESPERADO:
        faltan = ESQUEMA_ESPERADO - set(df.columns)
        sobran = set(df.columns) - ESQUEMA_ESPERADO
        errores.append(f"Esquema cambió. Faltan: {faltan} | Sobran: {sobran}")
        return errores

    if pd.to_numeric(df["precio"], errors="coerce").isna().any():
        cuantos = int(pd.to_numeric(df["precio"], errors="coerce").isna().sum())
        errores.append(f"{cuantos} precios no son numéricos")

    nulos = int(df["calificacion"].isna().sum())
    if nulos > 0:
        errores.append(f"{nulos} nulos en calificacion")

    cal = pd.to_numeric(df["calificacion"], errors="coerce")
    fuera = int(((cal < 3) | (cal > 5)).sum())
    if fuera > 0:
        errores.append(f"{fuera} calificaciones fuera de rango [3-5]")

    return errores

Bloque 5 · La herramienta profesional

Cuando el código a mano no escala: Pandera

Nuestro inspector funciona. Pero si Rappi mañana agrega 25 columnas más, cada una con sus reglas, serían decenas de if, fácil equivocarse, difícil de mantener. Aquí la industria dejó de hacerlo así.

🔗 Conexión con la Clase 2 — el mismo salto
Allá pasamos de "escribir SQL a mano como strings" → a SQLAlchemy (que lo hace por nosotros). Hoy pasamos de "validar a mano con if" → a Pandera. Es exactamente el mismo salto de madurez: de hacerlo a mano y frágil, a declararlo limpio y profesional.
📦 Definición técnica
Pandera es una librería para validar DataFrames de forma declarativa. En lugar de un if por regla, defines un esquema y Pandera revisa todo el DataFrame contra él de un solo golpe.
🌍 En la vida real
Pasamos de revisar cada empanada a mano… a una máquina de rayos X programada con las reglas una sola vez. Tú declaras las reglas; la máquina inspecciona todo el lote sola.

Bloque 6 · Que avise solo

Logging y alertas

Ya detectamos los problemas. Pero seguimos mirando la pantalla nosotros. A las 3am no hay nadie mirando la consola. Dejamos atrás el print y usamos logging.

📦 Definición técnica
Logging es el registro estructurado de lo que hace un programa, con niveles (INFO, WARNING, ERROR). A diferencia de print, lleva fecha/hora y nivel, y puede archivarse o enviarse a un sistema de monitoreo. Una alerta dispara una acción ante un evento crítico.
🌍 En la vida real
print es contarle algo a alguien que pasaba por ahí. Logging es la bitácora de vuelo del avión: queda registrado con hora exacta, se revisa después, y los eventos graves activan una alarma en cabina al instante.
🔗 Conexión con el camino
Fíjate en el patrón de hoy: cada herramienta nueva (Pandera, logging) reemplaza una versión casera (los if a mano, el print) por una profesional. Eso es exactamente "del notebook a producción", el lema de toda esta unidad.

Bloque 7 · Todo junto + el puente a SQL

El pipeline vigilado

Hasta ahora exploramos cada herramienta en el notebook. Ahora las unimos en el pipeline final, en un archivo .py (como en la Clase 2): leer con try/except, validar, alertar si falla, guardar si pasa, y verificar en SQL que lo guardado está sano.

🔗 Conexión con la Clase 2 — se cierra el círculo
En la Clase 2 construimos la base y aprendimos a guardar con SQLAlchemy. Hoy ese conocimiento regresa: cuando un feed pasa la validación, lo guardamos en una base SQL igual a la de la Clase 2, y le hacemos una consulta para verificar. El SQL de la Clase 2 no quedó en el aire — es el destino que hoy aprendimos a proteger.

El pipeline completo, con todas las guardas en orden

rappi_calidad/pipeline.py
import pandas as pd
import logging
from sqlalchemy import create_engine, text

logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s | %(levelname)s | %(message)s")
logger = logging.getLogger("pipeline_rappi")

ESQUEMA = {"pedido_id", "restaurante_id", "categoria",
           "ciudad", "precio", "calificacion"}

def enviar_alerta(mensaje):
    logger.error(f"ALERTA: {mensaje}")

def validar(df):
    errores = []
    if set(df.columns) != ESQUEMA:
        errores.append(f"Esquema cambió. Recibido: {set(df.columns)}")
        return errores
    if pd.to_numeric(df["precio"], errors="coerce").isna().any():
        errores.append("Hay precios no numéricos")
    if df["calificacion"].isna().any():
        errores.append(f"{int(df['calificacion'].isna().sum())} nulos en calificacion")
    return errores

def procesar_feed(ruta):
    try:
        df = pd.read_csv(ruta)
    except FileNotFoundError:
        enviar_alerta(f"No se encontró el archivo {ruta}")
        return None

    errores = validar(df)
    if errores:
        for e in errores:
            enviar_alerta(e)
        logger.warning(f"Feed {ruta} RECHAZADO. No se persiste.")
        return None

    logger.info(f"Feed {ruta} VÁLIDO. Persistiendo {len(df)} filas...")
    engine = create_engine("sqlite:///rappi_calidad.db")
    df.to_sql("pedidos_validados", engine, if_exists="replace", index=False)

    with engine.connect() as conn:
        total = conn.execute(
            text("SELECT COUNT(*) FROM pedidos_validados")).scalar()
        nulos = conn.execute(
            text("SELECT COUNT(*) FROM pedidos_validados "
                 "WHERE calificacion IS NULL")).scalar()
    logger.info(f"Verificación SQL → filas: {total}, nulos: {nulos}")
    return df
🔗 Este SQL es el mismo de la Clase 2 y será el de la Clase 4
SELECT COUNT(*) lo usamos en la auditoría de la Clase 2. La Clase 4 lo lleva al siguiente nivel con agregaciones complejas sobre esta misma base. Las tres clases tocan SQL, cada una a su profundidad: Clase 2 lo construyó, Clase 3 lo usa para verificar, Clase 4 lo exprime. No son tres temas; son tres profundidades del mismo camino.
⚠️ Recordatorio de la Clase 2
La consulta SQL va escrita directamente en el .py, nunca copiada desde un editor de texto enriquecido. Las comillas tipográficas (las curvas) rompen las queries.

?
¿Por qué 200 minutos es un problema de datos si 200 es un número válido?

Porque la validación de tipo (es un número entero, correcto) no garantiza la validación de negocio (es un número posible en la realidad). Un dato puede ser técnicamente correcto y aun así estar mal. Por eso existen las reglas de rango: capturan lo que el tipo solo no puede. 200 pasa el chequeo de "¿es entero?" pero falla el de "¿tiene sentido para una entrega?".
